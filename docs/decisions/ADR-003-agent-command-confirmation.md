# ADR-003：Agent 命令确认策略

## 状态
已被 2026-08-13 的两次修订取代（见文末「2026-08-13 修订」与「2026-08-13 再修订」）

## 日期
2026-07-21

## 背景
Agent 可以执行远程 shell 命令。用户既希望便捷（低摩擦），也希望安全（无静默破坏性操作）。按服务器信任对实验机很有用；生产主机需要更严格默认值。

## 决策
`run_remote_command` 确认策略：

1. 默认：始终弹出模态确认，并展示截断后的命令预览。
2. 若服务器启用 `agentCommandAutoApprove === true`，对非破坏性命令可跳过确认。
3. 若命令匹配明显破坏性启发式（`rm -r`、`mkfs`、`shutdown`、`reboot`、`poweroff`、`dd if=`），即使开启自动批准也 **始终** 确认。
4. 自动批准 **不会** 绕过：
   - SFTP 写授权
   - SSH 主机密钥信任
   - 资产导入 / 导出密码提示

## 备选方案

### 始终确认
- 优点：最安全
- 缺点：在受信任跳板机上做迭代运维几乎不可用
- 结论：不能作为唯一模式

### 一旦连接就始终自动执行
- 优点：无摩擦
- 缺点：误操作损害风险很高
- 结论：否决

### 完整 allowlist 语言
- 优点：精确
- 缺点：交互复杂；适合后续增强，不适合 MVP
- 结论：推迟到 P2 策略引擎

## 后果
- 破坏性检测是启发式，并不完备；扩展时要避免制造虚假安全感。
- 界面文案必须解释信任开关作用范围（仅影响命令）。
- 测试应覆盖：自动批准开启时，破坏性命令仍会提示确认。

## 2026-08-13 修订：黑名单改为只读白名单

原决策第 2、3 条把「破坏性正则不匹配」当作放行依据。该正则是一条黑名单，
`find / -delete`、`> /etc/passwd`、`chmod -R 777 /`、`curl … | sh`、
`dd of=… if=…`、`rm${IFS}-rf${IFS}/`、`truncate -s0 …`、`mv /etc/passwd /tmp`
全部不匹配，开启自动批准后零弹窗静默执行。上面「完整 allowlist 语言」被推迟的
理由是「交互复杂」，但威胁模型已经变了：调用方可能是被提示注入的 agent，不是
手滑的人，黑名单对它没有任何约束力。

修订后的策略：

1. 默认：始终弹出模态确认（不变）。
2. `agentCommandAutoApprove === true` 只对**只读命令白名单**免确认
   （`ls` / `cat` / `grep` / `ps` / `df` / `systemctl status` / `journalctl` 等）。
   命令含 `|`、`&`、`;`、`<`、`>`、反引号、`$`、括号、花括号、换行或反斜杠时
   一律退出白名单——因为此时行首那个白名单命令已经不能代表将要执行的东西。
3. 破坏性正则**保留但降级为纯警告标记**，只影响确认对话框上的红色提示，
   不再参与放行判断。
4. 第 4 条（不绕过 SFTP 写授权 / 主机密钥信任 / 资产导入导出口令）不变。

已知残留（有意接受）：白名单里的 `cat` / `grep` 能读取 `/etc/shadow` 之类的
敏感文件而不弹窗。本产品的读取面本来就不设确认门（`sftp_read_file` 同样如此），
确认门针对的是变更与执行；把读取也纳入需要另一个独立决策。

## 2026-08-13 再修订：只读管道放行

上一节第 2 条把 `|` 与 `>` `;` `&&` 放进同一个字符类，用户实测后反馈信任开关在
最常用的场景下失效：`netstat -tulnp` 免确认，`netstat -tulnp | grep 8080` 弹窗；
`cat /etc/os-release` 免确认，`cat /var/log/app.log | tail -50` 弹窗。排障几乎全靠
管道，于是开关等同于没开。

判断是对的，而且不是「用户嫌麻烦」那类反馈：**危险的不是管道本身，而是管道两端
是什么。** `cat x | grep y` 与 `cat x | sh` 被一视同仁，才是上一节真正的错误。

修订后的第 2 条：

2. `agentCommandAutoApprove === true` 对**只读命令白名单**免确认。命令按 `|` 分段，
   **每一段都必须独立通过同一套白名单规则**（含 `systemctl` / `journalctl` 的参数
   规则）才免确认；任何一段不合格就整条弹窗。`>` `<` `;` `&`（含 `&&` 与后台 `&`）、
   反引号、`$`、括号、花括号、换行、反斜杠**仍然一律拦**。`||` 是控制操作符不是管道，
   显式拒绝；空段（`cat x |`、`| grep y`）一律不合格。

这**不是**退回黑名单：放行的前提仍然是「每一段都在只读白名单内」，没有任何一条命令
因为「不像危险」而通过。上一节列出的 `find / -delete`、`curl … | sh`、`chmod -R 777 /`
等八条旧黑名单漏网，在本次修订后依旧全部弹窗，用例逐条钉住。

分段不做 shell 词法解析，引号里的 `|` 会被当成分隔符。这只会**多弹一次**，不会少弹：
真正会被执行的那一段总是紧跟在未加引号的 `|` 之后，因而必然也是朴素分段的段首；而把
段首藏进引号（`r"m" -rf /`）之后它就不再字面匹配白名单键。代价是 `grep "a|b" file`
这类无害命令会多弹一次窗，接受。
