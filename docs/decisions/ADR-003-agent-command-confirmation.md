# ADR-003：Agent 命令确认策略

## 状态
已被 2026-08-13 的三次修订取代（见文末「2026-08-13 修订」「2026-08-13 再修订」
与「2026-08-13 三修订：确认模型由白名单反转为黑名单」；**当前生效的是第三次**）

## 日期
2026-07-21

## 背景
Agent 可以执行远程 shell 命令。用户既希望便捷（低摩擦），也希望安全（无静默破坏性操作）。按服务器信任对实验机很有用；生产主机需要更严格默认值。

## 决策
`run_remote_command` 确认策略：

1. 默认：始终弹出模态确认，并展示截断后的命令预览。
2. 若服务器启用 `agentCommandAutoApprove === true`，对非破坏性命令可跳过确认。
3. 若命令匹配明显破坏性启发式（`rm -r`、`mkfs`、`shutdown`、`reboot`、`poweroff`、`dd if=`），即使开启自动批准也 **始终** 确认。
4. 自动批准 **不会** 绕过：
   - SFTP 写授权
   - SSH 主机密钥信任
   - 资产导入 / 导出密码提示

## 备选方案

### 始终确认
- 优点：最安全
- 缺点：在受信任跳板机上做迭代运维几乎不可用
- 结论：不能作为唯一模式

### 一旦连接就始终自动执行
- 优点：无摩擦
- 缺点：误操作损害风险很高
- 结论：否决

### 完整 allowlist 语言
- 优点：精确
- 缺点：交互复杂；适合后续增强，不适合 MVP
- 结论：推迟到 P2 策略引擎

## 后果
- 破坏性检测是启发式，并不完备；扩展时要避免制造虚假安全感。
- 界面文案必须解释信任开关作用范围（仅影响命令）。
- 测试应覆盖：自动批准开启时，破坏性命令仍会提示确认。

## 2026-08-13 修订：黑名单改为只读白名单

原决策第 2、3 条把「破坏性正则不匹配」当作放行依据。该正则是一条黑名单，
`find / -delete`、`> /etc/passwd`、`chmod -R 777 /`、`curl … | sh`、
`dd of=… if=…`、`rm${IFS}-rf${IFS}/`、`truncate -s0 …`、`mv /etc/passwd /tmp`
全部不匹配，开启自动批准后零弹窗静默执行。上面「完整 allowlist 语言」被推迟的
理由是「交互复杂」，但威胁模型已经变了：调用方可能是被提示注入的 agent，不是
手滑的人，黑名单对它没有任何约束力。

修订后的策略：

1. 默认：始终弹出模态确认（不变）。
2. `agentCommandAutoApprove === true` 只对**只读命令白名单**免确认
   （`ls` / `cat` / `grep` / `ps` / `df` / `systemctl status` / `journalctl` 等）。
   命令含 `|`、`&`、`;`、`<`、`>`、反引号、`$`、括号、花括号、换行或反斜杠时
   一律退出白名单——因为此时行首那个白名单命令已经不能代表将要执行的东西。
3. 破坏性正则**保留但降级为纯警告标记**，只影响确认对话框上的红色提示，
   不再参与放行判断。
4. 第 4 条（不绕过 SFTP 写授权 / 主机密钥信任 / 资产导入导出口令）不变。

已知残留（有意接受）：白名单里的 `cat` / `grep` 能读取 `/etc/shadow` 之类的
敏感文件而不弹窗。本产品的读取面本来就不设确认门（`sftp_read_file` 同样如此），
确认门针对的是变更与执行；把读取也纳入需要另一个独立决策。

## 2026-08-13 再修订：只读管道放行

上一节第 2 条把 `|` 与 `>` `;` `&&` 放进同一个字符类，用户实测后反馈信任开关在
最常用的场景下失效：`netstat -tulnp` 免确认，`netstat -tulnp | grep 8080` 弹窗；
`cat /etc/os-release` 免确认，`cat /var/log/app.log | tail -50` 弹窗。排障几乎全靠
管道，于是开关等同于没开。

判断是对的，而且不是「用户嫌麻烦」那类反馈：**危险的不是管道本身，而是管道两端
是什么。** `cat x | grep y` 与 `cat x | sh` 被一视同仁，才是上一节真正的错误。

修订后的第 2 条：

2. `agentCommandAutoApprove === true` 对**只读命令白名单**免确认。命令按 `|` 分段，
   **每一段都必须独立通过同一套白名单规则**（含 `systemctl` / `journalctl` 的参数
   规则）才免确认；任何一段不合格就整条弹窗。`>` `<` `;` `&`（含 `&&` 与后台 `&`）、
   反引号、`$`、括号、花括号、换行、反斜杠**仍然一律拦**。`||` 是控制操作符不是管道，
   显式拒绝；空段（`cat x |`、`| grep y`）一律不合格。

这**不是**退回黑名单：放行的前提仍然是「每一段都在只读白名单内」，没有任何一条命令
因为「不像危险」而通过。上一节列出的 `find / -delete`、`curl … | sh`、`chmod -R 777 /`
等八条旧黑名单漏网，在本次修订后依旧全部弹窗，用例逐条钉住。

分段不做 shell 词法解析，引号里的 `|` 会被当成分隔符。这只会**多弹一次**，不会少弹：
真正会被执行的那一段总是紧跟在未加引号的 `|` 之后，因而必然也是朴素分段的段首；而把
段首藏进引号（`r"m" -rf /`）之后它就不再字面匹配白名单键。代价是 `grep "a|b" file`
这类无害命令会多弹一次窗，接受。

## 2026-08-13 三修订：确认模型由白名单反转为黑名单（用户决策）

上一节修好了管道，但没有修白名单本身。用户在真机上继续实测：`top -bn1`、`last -n 10`、
`vmstat 1 5`、`lsof -i :8080`、`ss -tulnp`、`dig example.com` 仍然全部弹窗——它们不在那
29 个只读命令里。**白名单追不上真实环境的工具集**：一台机器上能用来排障的命令有几百个，
且随发行版、装了什么包、运维习惯而变；用户看到的现象是「信任开关时灵时不灵」。

**决策（用户明确要求，非安全评估结论）：反转为黑名单——命中才弹窗，其余放行。**

修订后的第 2 条：

2. `agentCommandAutoApprove === true` 时，命令按 `|`、`;`、`&&`、`||`、`&` 分段，
   **每一段的命令名都要过黑名单**，任一段命中即弹窗，全部未命中才免确认。命令名先归一化
   （剥掉路径只取 basename、转小写）再比对，`/bin/rm`、`/usr/bin/RM` 与 `rm` 等价。
   黑名单共 **441 个命令名**：423 个整名拦截，分 18 组（文件写入 / 权限属性 / 归档 / 磁盘与文件系统 /
   进程与作业 / 服务与内核 / 解释器与执行包装 / 包管理 / 网络传输与远程执行 / 账号与认证 /
   网络配置 / 容器与编排 / 编辑器与分页器 / 追踪调试 / 数据库客户端 / 引导与 initramfs /
   其它版本控制 / 其它状态变更）；另外 **18 个按参数判断**（`systemctl`、`hostnamectl`、
   `timedatectl`、`localectl`、`journalctl`、`ip`、`ss`、`find`、`dmesg`、`crontab`、`date`、
   `hostname`、`sysctl`、`git`、`ifconfig`、`route`、`ethtool`、`sort`），**参数判断不了时一律
   按命中处理**。还有 6 条命名族正则覆盖生成式名字：`mkfs.*`、`fsck.*`、`mount.*`/`umount.*`、
   带版本号的解释器（`python3.11`）、带版本号的编译器（`gcc-12`）、`systemd-*`/`ansible-*`/`grub*-*`。
3. **无法安全解析的形态一律弹窗，不查黑名单**：命令替换 `$(…)` 与反引号、任何重定向
   （`>` `>>` `<` `<<` `2>` `>&` 与进程替换）、换行、反斜杠转义；命令名位置出现引号
   （`"rm"`、`r''m`）；命令名不是一个普通名字（`{r,x}m` 花括号展开、`/bin/r?` 通配、
   `FOO=bar rm` 赋值前缀、裸 `.` 即 `source`）。**参数里的引号是正常的**，只有段首带引号才拒。
4. 黑名单没点名、但命令名写成路径的（`./deploy.sh`、`/tmp/payload`）同样弹窗：黑名单按名字
   工作，一个路径不是它能回答的问题。已点名的路径写法不受影响（`/usr/bin/systemctl status` 仍免确认）。
5. `looksDestructive` 保留，仍然只驱动确认框上的红色横幅，不参与放行判断。它与黑名单**粒度不同**：
   黑名单答「会不会改变状态」，横幅答「会不会毁数据」，`mkdir /tmp/x` 命中前者不命中后者。
   若让横幅跟随黑名单，受信任服务器上每一次弹窗都会亮红，等于没有横幅。
6. 第 4 条（不绕过 SFTP 写授权 / 主机密钥信任 / 资产导入导出口令）自始未变。

### 代价（不粉饰）

- **未知命令默认放行。** 这是黑名单的定义性缺陷，不是实现瑕疵。任何没被点名的二进制——自研运维
  脚本、`/usr/local/bin` 下的工具、发行版特有命令——在受信任服务器上不弹窗直接执行。白名单在这
  一点上严格更安全，我们是拿它换可用性。
- **收口靠的是解释器组与不可解析形态，不是「危险命令」组。** 未知名字要变成任意命令，通常要经过
  `sh`/`bash`/`python`/`perl`/`awk`/`sed`/`xargs`/`env`/`sudo`/`make`/`docker`，或经过
  `$(…)`/重定向/转义/引号——这些全部弹窗。**因此黑名单的实际强度取决于解释器与包装那一组是否完整。
  下一个人要补，先补那一组。**
- **参数规则是近似，方向统一 fail-safe。** `git` 用的是读子命令集合，`git branch`、`git tag`、
  `git config` 这类读写同名的子命令一律弹窗；`ifconfig eth0`、`route -A inet6` 这类只读形态也会
  多弹。多弹可接受，少弹不可接受。

### 已知拦不住的形态（供将来评估）

1. **未知名字的可执行文件**，只要不写成路径、不经过解释器：`myctl restart-all`、`deploy-prod`。
2. **交互式工具的交互破坏面**：`top` 必须放行（`top -bn1` 是本次修复的目标之一），而交互 `top` 有
   `k` 可以杀进程，`htop`/`atop` 同理。非交互 SSH 无 TTY 让它们大多起不来，但那是环境在保护，不是策略。
3. **读取面完全不设门**：`grep -r` 可以读遍全盘，`cat /etc/shadow` 不弹窗。与首版决策一致，
   确认门针对变更与执行；把读取也纳入需要另一个独立决策。
4. **shell 内建**：`export`、`ulimit`、`alias`、`cd` 未收录（只影响这一次的非交互 shell，不落盘）。
   但 `PATH=/tmp/x cmd` 这类赋值前缀被第 3 条拒掉。
5. **分段不做词法解析**：引号里的 `|`、`;`、`&` 会被当成分隔符。方向只会多分段（多弹）不会漏分段——
   真正会被执行的段总是紧跟一个未加引号的分隔符，因而必然也是朴素分段的段首。代价是
   `grep "a|b" file` 多弹一次。
6. **名字族正则只覆盖常见形态**：`python3.11` 拦得住，`/opt/py311/bin/python` 靠「路径即弹窗」兜底，
   而远端把解释器改名成 `mypython` 就拦不住。
7. **策略读的是命令行文本，不是远端 shell 的解析结果**：远端的 `alias rm=trash`、shell 函数、
   把危险程序改名塞进 `PATH`，本策略一无所知。

### 为什么不回到白名单再加长

这一轮已经试过（`e3a4c59` → `d87a4b3`）。29 条不够用，加到 100 条也不会够——「够用」的判据在每台
机器上都不一样。**两种失败模式不对称**：黑名单漏一个危险命令，可以补名单逐步收敛；白名单拦一个查询
命令，用户当场就要为无意义的弹窗点确认，最终要么关掉开关，要么养成无脑点确认的习惯——后者会让这道门
在真正需要它的时候也失效。
